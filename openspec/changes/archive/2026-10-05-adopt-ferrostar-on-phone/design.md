## Context

Ferrostar 0.57.0 ships React Native support as three packages in `stadiamaps/ferrostar`
under `react-native/`: `ferrostar-uniffi-react-native` (Rust core compiled per platform,
with generated bindings), `ferrostar-core-react-native` (tracking, off-route handling,
route requests; plain TypeScript over the bindings) and `ferrostar-maplibre-react-native`
(their map screen). None is on npm. Stadia's issue to publish them (stadiamaps/ferrostar#961)
was waiting on a refactor that merged on 2026-09-15; they are still unpublished on
2026-10-05.

Another team has run Ferrostar's core under Expo 57 / React Native 0.86 with their own
MapLibre map (stadiamaps/ferrostar#947), which is the shape chosen here.

The phone app is a continuous-native-generation Expo app: `ios/` and `android/` are
generated by prebuild and ignored. Position comes from `expo-location`
(`apps/mobile/lib/where-am-i.ts`). Street routes come from `@pinpoint/routing` through
`apps/mobile/lib/street-route.ts`, Stadia first, with the key in `config.stadia.apiKey`.

## Goals / Non-Goals

**Goals:**
- Prove, in a development build on iOS and Android, that Ferrostar's core tracks a route
  under Pinpoint's own map: the position moves along the line, the next turn is known, and
  leaving the route gets a new one.
- Leave #279 a working base and a recorded verdict.

**Non-Goals:**
- Ferrostar's map package. It is not installed.
- Anything visible outside a development build.
- Making the trial screen look finished. It uses Pinpoint's map and tokens because that is
  the point being proven, not because its layout will survive.
- Background tracking, spoken instructions, arrival behaviour, fallback to FOSSGIS while
  following. All #279.

## Decisions

### Build the two packages from the 0.57.0 tag and host the archives on a release of this repository

`.github/scripts/build-ferrostar.sh` checks out `stadiamaps/ferrostar` at tag `0.57.0`,
runs their own build (`ubrn build ios|android --release`, then each package's `prepare`),
and `npm pack`s `uniffi` and `core` into two `.tgz` files, printing their SHA-512. It
checks first for `rustup` with the iOS and Android targets, `cargo-ndk`, the Android NDK,
Xcode and `bun`, and stops naming whichever is missing (spec: *built once and installed
ready-made*).

The archives are attached to a GitHub release on this repository, tagged
`ferrostar-rn-0.57.0`. `apps/mobile/package.json` names each by its release URL; the
lockfile records its integrity hash, which is what pins the contents. The repository is
public, so CI downloads them with no token.

Core declares `"@stadiamaps/ferrostar-uniffi-react-native": "*"` as a dependency, which
pnpm would look up on npm and fail. Pointing that name at the release URL with an
`overrides` entry was tried and refused: pnpm 11's `blockExoticSubdeps` will not take a
dependency's own dependency from a URL, and turning that off would lift it for every
package in the workspace. So the script moves that one entry from `dependencies` to
`peerDependencies` before packing core, and `apps/mobile` supplies it directly. Core's
code is untouched.

Why not commit the archives: the bindings include a static library per platform and
architecture, which is tens of megabytes of binary in every clone forever. Why not a
private registry: installing would then need credentials.

When Stadia publishes, the URLs become `0.57.x` registry versions.

### Use Ferrostar's own Valhalla adapter, pointed at Stadia, for routes while following

Ferrostar needs a route with its turn-by-turn steps, which `@pinpoint/routing` does not
keep — it reads only the line, the distance and the time. Ferrostar's built-in Valhalla
adapter asks for and parses exactly what it needs, so it is pointed at Stadia's
`/route/v1` with the same key, the travel mode's Valhalla profile, and the app's language
as Valhalla's `language` option.

Only Stadia is asked while following. Falling back to FOSSGIS mid-trip is a #279 decision.

Recalculation is spaced by Ferrostar's minimum time before recalculating, set to 5
seconds, which keeps it well under the once-a-second limit `place-route` sets for the
device.

### Feed Ferrostar positions from `expo-location`, not from a new location library

Ferrostar takes positions through a `ManualLocationProvider`; the trial screen subscribes
with `expo-location` while it is open and forwards each update. No second location
library, no new permission text. For testing at a desk, the screen can switch to
Ferrostar's `SimulatedLocationProvider`, which walks the route on its own, and offers a
control that jumps the simulated position 150 metres off the line to force a new route.

### The trial screen is a route gated on `__DEV__`, reached by link

`apps/mobile/app/dev/follow.tsx`. When `__DEV__` is false it returns `<Redirect href="/" />`
before anything else renders. That file imports nothing of Ferrostar: the trial is
`components/follow-trial.tsx`, loaded with `lazy(() => import(…))` only when the screen
opens. Every route file is evaluated when the app starts, and importing Ferrostar installs
its compiled core into the JavaScript engine there and then; with the trial imported
eagerly, the development build reloaded itself when *Calculate route* was pressed, and did
not with it loaded on demand. Nothing of Ferrostar runs for anyone who never opens the
trial. It takes `to` (and optionally `mode`) from the link, so a
developer opens it with
`xcrun simctl openurl booted "pinpoint://dev/follow?to=135.7727,35.0037&mode=walking"`.
Nothing in the app links to it.

It draws Pinpoint's map with the route line from `@pinpoint/map`'s street-route form and
the person's dot as *where am I* draws it, and over it a small panel: the next
instruction, the distance to it, and whether a new route is being found. The
instruction's text is the router's, in the app's language. The words around it are named
sentences under `trial.follow.*`, in English and Spanish, so `check:wording` and the
literal lint hold here as everywhere.

The camera follows the position on this screen. That is a convenience for the trial, not
a decision for #279.

## Risks / Trade-offs

- **The native part does not build under Expo 57 / RN 0.86.** Ferrostar's example is on
  Expo 55 / RN 0.83. → Build iOS first; the bindings are C++ over JSI with a vendored
  xcframework, a different path from the Swift pods #947 had to write. If it cannot be
  made to build within this change, stop, record why on #279, and record the alternative
  (bridging Ferrostar's native iOS and Android kits ourselves, or following without
  Ferrostar) as the next ticket.
- **A stale native build hides the new module.** The phone gotchas in `CLAUDE.md` apply: a
  new native module is invisible to a build from before it. → Uninstall old builds and
  rebuild from an empty cache before concluding anything.
- **Stadia's free allowance.** Every return to the route is a request. → Look up the
  current allowance and work out the cost of a realistic day of following (an hour of
  walking, a few dozen recalculations); record the figure on #279.
- **Valhalla's Spanish addresses the reader** (*Gire a la izquierda*), where Pinpoint's
  Spanish is impersonal. Harmless on a trial screen. → Recorded on #279, which has to decide
  whether router text is shown as is.
- **The archive outlives its source.** If Stadia moves or deletes the tag, the script
  cannot rebuild it. → The release keeps the archives; the script pins a tag, not a branch.
